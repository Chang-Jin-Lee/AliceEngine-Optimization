- SceneFile::ApplyEntity()가 위험하다고 하는뎅
    
    ### A) SceneFile::ApplyEntity()의 엔티티 ID 처리 방식이 심각하게 위험함
    
    `ApplyEntity()` 시작이 이렇습니다:
    
    ```cpp
    EntityId id = world.CreateEntity();
    
    if (in.contains("id"))
    {
        id =static_cast<EntityId>(in["id"].get<std::uint32_t>());
        ...
    }
    
    ```
    
    이건 “CreateEntity로 생성한 id”와 “파일에 저장된 id”가 다를 때,
    
    - **실제로 생성된 엔티티(예: 3번)** 는 월드에 남고,
    - 컴포넌트는 **다른 id(예: 4번)** 에 붙습니다(하지만 4번은 generation 테이블에 없을 수 있음).
    
    결과:
    
    - “유령 엔티티”가 생기거나
    - `IsEntityValid()`가 거짓을 뱉는 엔티티가 생기거나
    - 나중에 `CreateEntity()`가 같은 id를 다시 뱉는 순간 충돌/오염
    
    지금은 `World::Clear()`가 `m_nextEntityId = 1`로 리셋되니까, 저장된 id들이 1..N 순서로 딱 맞아떨어지면 운 좋게 안 터집니다.
    
    하지만 **엔티티 삭제로 id가 건너뛰는 순간**(1,2,4 같은 씬)부터 재현됩니다.
    
    **권장 수정 방향**
    
    - “저장된 id를 그대로 쓰고 싶다”면: `World::CreateEntityWithId(id)` 같은 API를 만들고, `m_nextEntityId`/`m_entityGenerations`를 일관되게 갱신해야 합니다.
    - “id는 런타임 식별자일 뿐”이면: 씬 파일에서 id 저장을 버리고, 로드 시 새 id를 부여하고, 참조가 필요한 경우(부모-자식, 링크 등)만 별도 remap 테이블로 해결해야 합니다.
- 키네마틱 터진거 고침(기록용)
    
    그 “...? 뭐임?”이 맞는 반응이고, 결론부터 말하면 **네가 PhysX의 내부 불변식(invariant)을 어긴 거고**, 위치를 옮기니 그 불변식이 다시 만족돼서 조용해진 거야.
    
    ### `eENABLE_POSE_INTEGRATION_PREVIEW`가 대체 뭐길래 addActor에서 터지냐
    
    이 플래그는 그냥 “옵션 하나 켜기”가 아니라,
    
    - **씬이 시뮬레이션 중에** 바디의 새 포즈를 “조기(early)”로 보고하기 위해
    - 그 바디를 **씬 내부의 ‘pose preview 리스트’ 같은 관리 구조에 등록**시키는 용도야.
    - 그래서 `PxSimulationEventCallback::onAdvance()`에서 그 바디들이 전달되는 거고. ([nvidia-omniverse.github.io](https://nvidia-omniverse.github.io/PhysX/physx/5.6.0/_api_build/structPxRigidBodyFlag.html))
    
    즉, 이 플래그는 **씬 레벨 자료구조랑 연결되는 성격**이야.
    
    근데 너는 “씬에 들어가기 전에(actor->getScene()==nullptr)” 그걸 켰지? 그러면 PhysX 입장에선:
    
    > “야 너 이 바디는 preview 리스트에 있어야 하는데… 아직 씬도 없는데 왜 켰냐?”
    > 
    
    가 되는 거고, **addActor 과정에서 내부 상태 정리/활성·비활성 처리**가 돌면서
    
    “리스트에 있어야 한다”는 가정이 깨져서 assert가 터지는 패턴이 딱 나온다.
    
    이게 PhysX 3.4에서도 똑같은 증상( `isInPosePreviewList` assert )으로 보고된 적 있음. ([GitHub](https://github.com/NVIDIAGameWorks/PhysX-3.4/issues/80?utm_source=chatgpt.com))
    
    (5.5에서 완전히 사라졌다고 단정 못 하지만, 너 케이스처럼 아직도 밟을 수 있는 지뢰인 셈)
    
    ---
    
    ### “오브젝트당 2번씩” 터진 이유
    
    보통 이런 assert는 **한 번의 addActor 콜스택 안에서도 여러 군데에서 같은 조건을 재확인**해.
    
    예를 들면:
    
    - “시뮬레이션 오브젝트 생성 시점”에서 한 번
    - “초기 sleep/activation 상태 정리(activate/deactivate)”에서 한 번
    
    그래서 네가 보기엔 **addActor 줄에서 2번 멈추는 것처럼** 보일 수 있어. (실제로는 같은 add 과정에서 내부 체크가 2번)
    
    ---
    
    ### 네가 한 수정이 왜 ‘정답’이냐
    
    `scene->addActor(*a)` **이후**에 플래그를 켜면, 그 순간엔
    
    - actor가 씬을 알고 있고 (`getScene()!=nullptr`)
    - PhysX가 그 씬의 내부 리스트에 **정상 등록**할 수 있어서
        
        불변식이 깨지지 않는다.
        
    
    너가 옮긴 위치가 “안전한 운영 방식”인 이유가 이거야.
    
    ---
    
    ### 추가로 한 줄 조언 (안 하면 또 비슷한 거 밟음)
    
    **씬 내부 리스트/콜백/이벤트에 연관된 플래그들**(이런 “등록형” 플래그)은 습관적으로:
    
    - **생성 단계(CreateXXX)** 에서 켜지 말고
    - **FlushPending에서 addActor 직후**에 “PostAdd 설정”으로 몰아넣어.
    
    그리고 이 플래그는 어차피 `onAdvance()`를 쓸 때만 의미가 있으니, 실제로 필요 없는 바디까지 전부 켜면 오버헤드만 늘어. ([nvidia-omniverse.github.io](https://nvidia-omniverse.github.io/PhysX/physx/5.5.0/_api_build/classPxSimulationEventCallback.html))
    
    요약: 네가 만난 건 “키네마틱 때문에 액터가 2개로 분열” 같은 게 아니라, **씬에 들어가기 전 ‘씬-연동 플래그’를 건드린 순서 버그/지뢰**였고, 네 수정이 그 지뢰를 피한 거야.
    

터레인 상태를 참조로 잡아두고 원본을 삭제했었슴 머쓱

- 터레인에서 있었던 문제 해결 방법
    
     **명백한 UB(정의되지 않은 동작: use-after-free / 컨테이너 메모리 오염)** 가 있어. 그게 메모리를 망가뜨린 다음, 씬 전환 정리 단계에서 `owned->Destroy()` 같은 곳이 “가끔” 터지는 형태로 나타나는 거야.
    
    핵심은 **Terrain 갱신 루프**에 있음. (`PhysicsSystem.cpp`의 “5. Terrain 변경 감지…” 블록)
    
    ---
    
    ## 1) 진짜 원인: TerrainState 참조 잡아놓고, 그걸 지워버림 (use-after-free)
    
    현재 코드 흐름:
    
    ```cpp
    auto it = m_lastTerrains.find(entityId);
    ...
    TerrainState& state = it->second;
    
    if (geomChanged)
    {
        if (terrain.physicsActorHandle != nullptr)
            DestroyPhysicsActor(entityId);   // <-- 여기서 m_lastTerrains.erase(entityId) 해버림
        ...
        state.lastGeomKey = geomKey;         // <-- 이미 지워진 state를 계속 씀 (UB)
    }
    ...
    state.layerBits = ...
    
    ```
    
    근데 `DestroyPhysicsActor()` 끝부분에 이게 박혀있지?
    
    ```cpp
    m_lastTerrains.erase(entityId);
    ```
    
    즉, **참조(`TerrainState& state`)는 그대로인데, 참조 대상은 erase로 증발**.
    
    그 다음 줄에서 `state.*` 쓰는 순간부터는 메모리 오염 랜덤파티 시작이야. “확률적으로” 터지는 버그의 전형적인 냄새지.
    
    ---
    
    ## 2) 이 UB가 “특히 Terrain 씬에서” 잘 터지는 이유 (트리거가 있음)
    
    Terrain 첫 등록 시에 너 코드가 **heightSamples가 비면 자동으로 resize로 채우잖아**:
    
    ```cpp
    if (terrain.heightSamples.empty() && terrain.numRows >= 2 && terrain.numCols >= 2)
        terrain.heightSamples.resize(expectedSamples, 0.0f);
    
    ```
    
    그런데 너는 `geomKey`를 **resize 이전에 계산**하고 있어:
    
    ```cpp
    const uint64_t geomKey = MakeTerrainGeomKey(terrain); // heightSamples.size() 포함
    
    ```
    
    - 처음엔 size=0 → `geomKey`가 “0샘플” 기준으로 저장됨
    - resize 후 다음 프레임엔 size=expectedSamples → `geomChanged == true`가 됨
    - 그 프레임에 `DestroyPhysicsActor()` 호출 → `m_lastTerrains.erase()` → `state` 참조는 즉시 썩음
    
    즉, **heightSamples가 비어있는 Terrain을 로드하는 순간**, 다음 프레임에 `geomChanged`가 거의 확정적으로 한 번 발생하고, 그때 UB를 밟을 확률이 커져.
    
    그 UB로 `m_entityToActor`나 `unique_ptr` 내부까지 메모리 오염이 번지면, 씬 전환 정리에서 “오너가 없다” 같은 이상한 형태로 터지는 거고.
    
    ---
    
    # 해결: Terrain 루프를 “erase 안전”하게 고쳐라
    
    `PhysicsSystem.cpp`의 Terrain 블록을 아래처럼 바꿔. 포인트는 2개:
    
    1. **heightSamples 자동 생성 후에 geomKey 계산**
    2. `geomChanged`에서 `DestroyPhysicsActor()` 호출 후에는 **기존 iterator/reference를 절대 쓰지 말고**, 상태를 새로 넣고 `continue`
    
    ---
    
    ## 4) 왜 이게 네가 본 “오너 없음” 크래시로 보였나
    
    이 UB는 `unordered_map` 내부 버킷/노드 메모리를 망가뜨릴 수 있고, 그 결과로:
    
    - `m_entityToActor`의 `unique_ptr`(owned)가 깨져서 null/가비지처럼 보이거나
    - `owned->Destroy()` 호출 시 vtable/this 포인터가 망가져서 크래시
    - “가끔”만 터짐 (메모리 레이아웃/타이밍/할당 상태에 따라)
    
    딱 네가 말한 증상하고 일치한다.
    
    ---
    
    이거 고치면 “터레인 씬 → 다른 씬” 전환 크래시는 상당 확률로 끝날 거야. 그리고 끝나야 정상이고.
    
    지금 상태는 PhysX가 문제가 아니라, **너의 상태관리 코드가 메모리를 불태우고 있는 것**이 문제다.

    ## 1) 데드락이 생기는 구조
    
    ### 게임 스레드(메인 스레드) 쪽: `Step()`
    
    `PhysXWorld::Step()`에서 이걸 함:
    
    ```cpp
    SceneWriteLock wl(impl->scene, impl->enableSceneLocks);
    impl->scene->simulate(fixedDt);
    impl->scene->fetchResults(true);
    
    ```
    
    즉, **`lockWrite()`를 잡은 채로 simulate → fetchResults까지 쭉 들고 있음.**
    
    (주석에도 “다른 스레드가 query/add/remove 못 하게”라고 써놨지. 의도는 맞음.)
    
    ### 물리 시뮬레이션 스레드(PhysX worker) 쪽: `onContactModify()`
    
    `PxContactModifyCallback::onContactModify()`는 **시뮬레이션 중간에 PhysX 워커 스레드에서 호출될 수 있음.**
    
    너 코드도 그 콜백 안에서 “사용자 콜백(cb)”을 호출해:
    
    ```cpp
    cb(pair, user);
    
    ```
    
    ### 문제의 순간: 사용자 콜백이 `Raycast/Overlap` 같은 쿼리를 호출하면?
    
    너 쿼리 함수들은 전부 이런 패턴이야:
    
    ```cpp
    SceneReadLock rl(impl->scene, impl->enableSceneLocks);// lockRead()
    scene->raycast(...)
    
    ```
    
    그럼 상황이 이렇게 됨:
    
    1. **메인 스레드**가 `lockWrite()` 잡고 `simulate()` 돌리는 중
    2. **워커 스레드**가 `onContactModify()` 들어옴
    3. 사용자 콜백에서 `world->Raycast()` 호출
    4. `Raycast()`가 `lockRead()` 시도 → **메인 스레드가 write lock을 잡고 있으니 대기**
    5. 근데 메인 스레드는 `fetchResults(true)`에서 **워커 스레드들이 끝나길 기다리는 중**
    6. 워커 스레드는 `lockRead()`에서 **메인 스레드가 lock 풀길 기다리는 중**
    
    👉 서로 “너 먼저” 하면서 **영원히 안 끝남 = 데드락**.
    
    이거 진짜 흔한 패턴이라, PhysX/Unity/UE 계열에서도 “contact modify 같은 시뮬레이션 콜백 안에서 쿼리/씬 접근 하지 마라”가 정석 경고야.
    
    ---
    
    크래시/UB/데드락으로 이어질 수 있는 포인트
    (A) `userData`를 포인터 값으로 인코딩하는 방식 — **비정상 포인터(Non-canonical) 위험**
    
    ```cpp
    constuint64_t combined = (worldEpoch <<32) | (entityId +1);
    returnreinterpret_cast<void*>(static_cast<std::uintptr_t>(combined));
    
    ```
    
    - 이건 “포인터처럼 보이는 정수”를 PhysX `void* userData`에 넣는 트릭인데,
    - **Windows x64는 “캐노니컬(canonical) 주소” 규칙**이 있어서, 상위 비트가 특정 형태를 만족하지 않으면 “그냥 저장만 해도” 런타임에서 문제를 일으킬 수 있는 경우가 있어.
    - 특히 `worldEpoch`가 커져서 `combined` 상위 비트가 커지면 **non-canonical pointer**가 될 수 있음.
    - 현실적으로 씬 전환을 6만 번 넘게 안 하면 괜찮을 가능성이 크긴 한데, “구조적으로 안전하냐?” 묻는다면 **안전하다고 말 못 함**.
    
    **개선 권장**
    
    - (가장 안전) 별도 테이블/풀에 `UserData{epoch, entityId}` 구조체를 저장하고 그 포인터를 넣기
    - (차선) 인코딩 비트를 48bit 내(또는 47bit 내)로 제한해서 canonical 보장 (epoch를 16bit로 제한 등)
    - (또 차선) epoch 비교를 유지하되 pointer로 보이는 값이 항상 canonical이 되게 마스킹
        
        
        ### (D) 조인트 in-place 업데이트가 scene lock 없이 PhysX 오브젝트를 만짐
        
        `PhysicsSystem`에서
        
        ```cpp
        itJoint->second->SetBreakForce(...);
        itJoint->second->SetCollideConnected(...);
        
        ```
        
        `PhysXJoint::SetBreakForce/SetCollideConnected`는 **scene lock을 안 잡고 PhysX joint를 직접 만져**.
        
        지금 엔진 루프가 단일 스레드로만 이걸 호출하면 보통 괜찮지만,
        
        - “나중에” 스크립트/잡 시스템/에디터 UI 스레드에서 만지는 순간 바로 레이스로 터질 수 있음.
        
        **개선 권장**
        
        - Joint setter에도 `SceneWriteLock` 걸어버리는 게 안전.
        - 또는 “조인트 변경도 pending queue”로 넘겨서 `Flush()` 타이밍에만 적용.

- GUID 요청 내역
    
    ## 1) 씬 저장/로드에서 parent 복원: `_parentId` 버리고 “GUID 기반 2-pass 로드”로 가야 함
    
    ### 왜?
    
    지금 `SceneFile.cpp`는 저장 시 `_parentId`를 넣는데(좋은 시도),
    
    로드(`ApplyEntity`)는 **새 EntityId를 생성**하니까 저장된 parent id랑 매칭이 안 돼. 즉, “parent 저장”이 사실상 무의미해.
    
    ### 해결: `IDComponent(Guid)` 추가 + 저장/로드 2번 돌기
    
    - 각 엔티티에 **영구 식별자 GUID(64-bit)**를 붙임
    - 저장: `guid`, `parentGuid` 저장
    - 로드:
        1. 엔티티들 먼저 전부 만들고 guid→EntityId 맵 생성
        2. parentGuid로 parent 연결
    
    ### (A) `IDComponent` 하나 만들기
    
    ```cpp
    // Components/IDComponent.h
    #pragma once
    #include<cstdint>
    
    namespace Alice
    {
    structIDComponent
        {
            std::uint64_t guid =0;
        };
    }
    
    ```
    
    ### (B) 새로 생성하는 곳마다 IDComponent도 붙이기
    
    - `World::CreateEmpty/CreateCube/CreateCamera/...`
    - `SceneFile::ApplyEntity`
    - `EditorCore::RestoreEntityFromJson` (삭제 Undo 복원)
    
    GUID 생성은 간단히 이렇게:
    
    ```cpp
    static std::uint64_tNewGuid()
    {
    static std::mt19937_64 rng{ std::random_device{}() };
    static std::uniform_int_distribution<std::uint64_t> dist;
    returndist(rng);
    }
    
    ```
    
    ### (C) `SceneFile.cpp` 저장 포맷 변경(버전 올려)
    
    저장할 때:
    
    - `guid` 저장 (uint64는 JSON에서 애매하면 **string**으로 저장 추천)
    - parent는 `_parentGuid` 저장
    
    로드할 때(핵심 2-pass):
    
    ```cpp
    std::unordered_map<std::uint64_t, EntityId> guidToEntity;
    structPendingParent { EntityId child; std::uint64_t parentGuid; };
    std::vector<PendingParent> pending;
    
    // PASS 1: 생성 + 컴포넌트 복원 + guid 맵
    for (auto& e : entities)
    {
        EntityId id = world.CreateEntity();
    
    // Transform 필수
    auto& t = world.AddComponent<TransformComponent>(id);
    FromJson(t, e["Transform"]);
    
    // IDComponent
    auto& idc = world.AddComponent<IDComponent>(id);
        idc.guid =ParseGuid(e["guid"]);// 없으면 NewGuid()
    
        guidToEntity[idc.guid] = id;
    
    if (e.contains("_parentGuid"))
            pending.push_back({ id,ParseGuid(e["_parentGuid"]) });
    }
    
    // PASS 2: parent 연결 (로드는 keepWorld 필요 없음)
    for (auto& p : pending)
    {
    auto it = guidToEntity.find(p.parentGuid);
    if (it != guidToEntity.end())
            world.SetParent(p.child, it->second,/*keepWorld=*/false);
    }
    
    ```
    
    이거 하면 씬 저장/로드 parent 복원이 “진짜로” 동작해.

    ### `LoadFromRoot()` - 2-Pass 로드 구현
    
    ```cpp
    static bool LoadFromRoot(World& world, const JsonRttr::json& root)
    {

        // 2-pass 로드: GUID 기반 parent 복원
        std::unordered_map<std::uint64_t, EntityId> guidToEntity;
        std::vector<std::pair<EntityId, std::uint64_t>> pendingParents;
    
        // PASS 1: 엔티티 생성 + 컴포넌트 복원 + GUID 맵 생성
        for (const auto& e : *itEntities)
        {
            if (!ApplyEntity(world, e, guidToEntity, pendingParents))
                return false;
        }
    
        // PASS 2: parent 연결 (keepWorld=false, 로드이므로)
        for (const auto& [childId, parentGuid] : pendingParents)
        {
            auto it = guidToEntity.find(parentGuid);
            if (it != guidToEntity.end())
            {
                world.SetParent(childId, it->second, false);
            }
        }
    
        return true;
    }
    
    ```

    ### 자동 적용되는 엔티티 생성 함수들
    
    - `World::CreateEntity()` - 모든 엔티티 생성의 기반
    - `World::CreateEmpty()`
    - `World::CreateCube()`
    - `World::CreateCamera()`
    - `World::CreatePointLight()`
    - `World::CreateSpotLight()`
    - `World::CreateRectLight()`
    - `SceneFile::ApplyEntity()` - 씬 로드 시
    - `EditorCore::RestoreEntityFromJson()` - Undo/Redo 복원 시
    - `Prefab::InstantiateFromFile()` - 프리팹 인스턴스화 시
    
    ### 씬 파일 포맷 변경
    
    - 저장 형식: JSON에 `guid` (string), `_parentGuid` (string) 추가
    - 호환성: 기존 파일은 GUID가 없으면 자동 생성
    - 버전: 기존 버전과 호환 (GUID 없으면 새로 생성)

    ### 8. 주요 개선사항
    
    1. Parent 관계 복원 정확도 향상
        - 기존: `_parentId` 저장했으나 로드 시 새 EntityId 생성으로 매칭 실패
        - 개선: GUID 기반으로 정확한 parent 복원
    2. 영구 식별자 제공
        - EntityId는 씬 로드 시 변경되지만, GUID는 유지
        - 프리팹, 참조 등에서 안정적 식별 가능
    3. 2-Pass 로드로 순서 독립성 확보
        - 엔티티 생성 순서와 무관하게 parent 관계 복원 가능
    
    ---
    
    ### 9. 데이터 흐름
    
    ```
    엔티티 생성
      ↓
    IDComponent 자동 추가 + GUID 생성
      ↓
    씬 저장 시: guid, _parentGuid 저장
      ↓
    씬 로드 시:
      PASS 1: 엔티티 생성 + GUID 맵 구축
      PASS 2: GUID로 parent 연결
    
    ```
    
    이 변경으로 씬 저장/로드 시 parent 관계가 정확히 복원됩니다.
