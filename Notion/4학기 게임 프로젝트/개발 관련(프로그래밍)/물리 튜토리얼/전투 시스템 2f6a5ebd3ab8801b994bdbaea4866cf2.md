# 전투 시스템

- 명령서
    
    아래는 **“의도/현실/이벤트 → FSM → Resolver → Apply → 다음 프레임”** 구조를 다른 AI(또는 팀원)에게 그대로 던져서 *같은 그림을 떠올리게 만드는* 설명서야.
    
    ---
    
    # 전투 구조 설명서 (Intent / Sensors / Events + FSM / Resolver)
    
    ## 0. 목표
    
    소울라이크 1:1 전투에서
    
    - **입력/AI**로 행동을 선택하고
    - **무기 스윕/히트박스**로 HitEvent를 만들고
    - **가드/무적/패리/피격**을 정확히 판정한 뒤
    - **피격 시 캔슬/경직/체력 감소** 같은 결과를 안정적으로 반영한다.
    
    중요한 요구:
    
    - 한 프레임 안에서 “누가 먼저 봤는지”에 따라 결과가 뒤집히지 않게 **Update 순서를 고정**한다.
    - FSM과 Resolver의 책임을 분리해서 디버깅/확장이 쉬운 구조로 만든다.
    
    ---
    
    ## 1. 핵심 개념 5개 (모듈 경계)
    
    모듈이 서로 직접 호출로 얽히지 않고, 아래 “계약 타입”으로만 소통한다.
    
    1. **Intent(의도)**
        
        “하고 싶다” 입력값. 플레이어 입력 또는 보스 AI가 생성.
        
        예: moveAxis, attackPressed, guardHeld, dodgePressed, useItemPressed
        
    2. **Sensors(현실/상태)**
        
        “지금 사실” 값. 월드/캐릭터의 실제 상태 요약.
        
        예: dt, hp/stamina, isGrounded, isBlocked, target 거리/각도, 현재 속도
        
    3. **HitEvent(원천 이벤트)**
        
        무기 스윕/히트박스에서 생성된 충돌 사실.
        
        예: attackerId, victimId, attackInstanceId, hitPos/normal, rawDamage
        
    4. **ActionState + ActionFlags(FSM 출력)**
        
        FSM이 산출하는 행동 상태 + “판정 윈도우 플래그(스위치)”.
        
    - ActionState: Idle/Move/Attack/Dodge/Guard/Hitstun/Dead/UseItem…
    - Flags: guardActive, invulnActive, parryWindowActive, hitActive, canBeInterrupted …
    1. **CombatEvent(지연 이벤트) + Commands(커맨드)**
        
        Resolver/Apply가 만들어 FSM 또는 엔진이 소비하는 결과.
        
    - Deferred CombatEvent: OnHit, OnGuarded, OnParried, OnDeath … (다음 프레임 FSM이 읽음)
    - Immediate Commands: ApplyDamage, ConsumeStamina, ForceCancelAction, DisableTrace, PlayAnim, MoveDelta …
    
    ---
    
    ## 2. 책임 분리(절대 규칙)
    
    구조가 망가지지 않게 하는 **강제 규칙**.
    
    ### FSM(ActionFsm)
    
    - 입력: Intent + Sensors + DeferredEvents(지난 판정 결과)
    - 출력: ActionState + ActionFlags + Commands(애니/이동/트레이스 요청)
    - **금지**: 데미지/스태미나 같은 리소스를 직접 깎지 않는다.
    - **역할**: “내가 지금 무엇을 하고 있고(상태), 지금 판정이 열려있나(플래그)”를 결정한다.
    
    ### Resolver(CombatResolver)
    
    - 입력: HitEvent + victim의 ActionFlags(+ 전면 판정/스태미나 등)
    - 출력: ResolveResult(Guarded/Hit/Ignored/Parried) → Immediate Commands + DeferredEvents
    - **금지**: FSM 상태를 직접 변경하지 않는다(= 상태 강제 전환 금지).
    - **역할**: “이 히트가 유효한가? 가드인가? 무시인가?”를 최종 판정한다.
    
    ### Apply(CombatApply)
    
    - 입력: Immediate Commands
    - 처리: HP/스태미나 실제 반영, 캔슬 플래그/트레이스 OFF 같은 즉시 처리
    - 출력: 필요하면 OnDeath 같은 DeferredEvent 추가 생성
    - **역할**: “이번 프레임 즉시 반영해야 하는 것”을 한 곳에서 처리한다.
    
    ### Movement/CCT
    
    - 입력: FSM이 낸 이동 요청(DesiredMoveDelta 또는 DesiredVelocity)
    - 출력: 실제 이동(ActualDelta), isBlocked, isGrounded 등 → 다음 프레임 Sensors가 읽음
    - **역할**: 벽/바닥/슬라이드/스텝 같은 현실 물리 해결
    
    > Resolver는 이동을 직접 시키지 않는다. 이동은 FSM→CCT.
    > 
    
    ---
    
    ## 3. Update 루프(프레임 순서) — 이 순서가 “진실”
    
    CombatSession(오케스트레이터)에서 아래 순서로 고정한다.
    
    ### 프레임 N
    
    1. **Intent 생성**
        
        플레이어 입력/보스 AI가 Intent를 만든다.
        
    2. **Sensors 갱신**
        
        현재 hp/stamina, 이동 상태(grounded/blocked), 타겟 거리/각도 등 현실을 센서로 만든다.
        
    3. **FSM Update (player/boss 각각 1회)**
        
        입력: Intent + Sensors + (이전 프레임에서 들어온 DeferredEvents)
        
        출력: ActionState + Flags + Commands
        
    - 예: Guard 상태면 guardActive=true
    - 예: Dodge 상태 특정 구간이면 invulnActive=true
    - 예: Attack 상태 특정 구간이면 hitActive=true
    1. **FSM Commands 실행 (Bridges)**
        
        애니 재생, 이동 요청, 트레이스 ON/OFF 등 엔진에 반영.
        
        (엔진 호출은 Bridge에서만)
        
    2. **WeaponTrace/Hitbox → HitEvent 생성**
        
        이번 프레임의 실제 Transform을 기반으로 스윕/충돌을 돌려 HitEvent를 생성하여 버스에 push.
        
    3. **Resolver 처리**
        
        HitEvent를 소비하면서 victim Flags를 보고 판정한다.
        
        판정 결과는:
        
    - Immediate Commands: ApplyDamage/ConsumeStamina/ForceCancel/DisableTrace…
    - DeferredEvents: OnHit/OnGuarded/OnParried…
    1. **Apply 처리(즉시 반영)**
        
        Immediate Commands를 실제 hp/stamina 등에 반영하고, 필요하면 OnDeath 이벤트도 만든다.
        
    2. **DeferredEvents 저장**
        
        OnHit 같은 DeferredEvents를 버스에 저장한다(다음 프레임 FSM이 읽는다).
        
    
    ### 프레임 N+1
    
    FSM은 DeferredEvents(OnHit 등)를 입력으로 받아 상태 전환:
    
    - UseItem 중 OnHit → Hitstun으로 전환
    - Guard 중 OnGuarded → GuardRecoil(선택)로 전환
    - hp<=0 또는 OnDeath → Dead로 전환
    
    ---
    
    ## 4. Resolver 판정 우선순위(표준 룰)
    
    Resolver는 base 상태(Guard/Dodge)를 직접 보지 말고 **Flags를 1순위**로 본다.
    
    권장 우선순위:
    
    1. invulnActive → Ignored
    2. parryWindowActive && 전면 → Parried
    3. guardActive && 전면 && stamina>0 → Guarded
    4. else → Hit
    
    이렇게 해야 “가드 모션이지만 아직 guardActive가 안 열린 프레임” 같은 튜닝이 정확히 반영된다.
    
    ---
    
    ## 5. 즉시 처리 vs 지연 처리(왜 나누는가)
    
    ### Immediate(같은 프레임 즉시)
    
    - ApplyDamage/ConsumeStamina(수치 반영)
    - 피격 시 공격 캔슬/트레이스 OFF(중복 히트 방지)
    - 히트스톱 같은 타이밍 민감 연출
    
    ### Deferred(다음 프레임 FSM이 반응)
    
    - OnHit → Hitstun 전환
    - OnGuarded → 가드 반동/스태미나 처리 반영
    - OnDeath → Dead 전환
    
    > 즉시 처리는 “당장 끊어야 안정적인 것”, 지연 처리는 “FSM이 상태 전이 규칙대로 반응해야 하는 것”.
    > 
    
    ---
    
    ## 6. “포션 마시다가 맞으면?” 예시
    
    - FSM: UseItem 상태, canBeInterrupted=true, invulnActive=false
    - HitEvent 발생
    - Resolver: Hit 판정 → Immediate: ApplyDamage + ForceCancelAction + DisableTrace / Deferred: OnHit
    - Apply: HP 감소 + 캔슬 플래그 세팅
    - 다음 프레임 FSM: OnHit 보고 UseItem → Hitstun
    
    Resolver가 FSM 상태를 직접 바꾸는 게 아니라, **OnHit 이벤트로 FSM이 바꾸게 한다.**
    
    ---
    
    ## 8. 금지사항 (아래 사항들이 꼭 지켜져야함)
    
    - FSM이 HP/스태미나를 직접 수정하는 로직 금지
    - Resolver가 FSM 상태를 직접 변경하는 로직 금지
    - 한 프레임에 FSM을 두 번 호출하는 구조 금지
    - Resolver가 state 이름으로 분기하는 것 금지(Flags 우선)

## 1. **스크립트 (엔티티에 붙이는 것)**

| 파일 | 역할 | 붙이는 대상 |
| --- | --- | --- |
| **C_CombatSession** | 전투 루프 총괄. 플레이어/보스 Fighter·FSM·이벤트버스·리졸버를 갖고, 매 프레임 Intent → Sensors → FSM → Command → 적용 순서로 돌림. | **씬의 매니저용 엔티티** (빈 오브젝트 등). `m_playerGuid`, `m_bossGuid`로 플레이어/보스 엔티티를 찾음. |
| **C_PlayerInputSource** | 키보드/마우스 입력을 읽어서 `Combat::Intent`(이동·공격·가드·회피 등)로 변환. | **플레이어가 조작하는 캐릭터 엔티티** (플레이어 엔티티). |
| **C_BossBrain** | 보스 AI. 타겟(플레이어)과의 거리/각도 보고 공격·이동 등 `Combat::Intent` 생성. | **보스/적 캐릭터 엔티티** (보스 엔티티). |

## 3. **전투 로직 클래스 (스크립트 아님, Session이 소유)**

| 파일 | 역할 | 소유/사용처 |
| --- | --- | --- |
| **C_Fighter** | 한 캐릭터의 전투 상태(HP, 스태미나, 팀, 상태, 플래그 등)와 `BuildSensors`/`Snapshot` 제공. | `C_CombatSession`이 플레이어·보스용 `Fighter` 인스턴스 2개 보유. |
| **C_ActionFsm** | Intent + Sensors + 이벤트로 상태(Idle/Move/Attack/Dodge/Guard/Hitstun/Dead) 전이, `FsmOutput`(상태·플래그·Command 목록) 반환. | `C_CombatSession`이 `playerFsm`, `bossFsm` 2개 보유. |
| **C_CombatEventBus** | 프레임 단위 Hit 이벤트 수집, 지연 CombatEvent(OnHit/OnGuarded/OnParried 등) 보관·조회. | `C_CombatSession`이 하나 보유하고 매 프레임 ClearFrame. |
| **C_CombatResolver** | Hit 이벤트 + 공격자/피격자 스냅샷으로 데미지·스태미나·경직·애니 등 `Command` 리스트 생성. | `C_CombatSession`이 하나 보유하고 Hit 처리 시 사용. |

---

## 4. **붙이는 대상 요약**

- **C_CombatSession** → 씬에서 전투를 돌리는 **매니저 엔티티** 하나 (그 엔티티의 Guid를 플레이어/보스 찾는 데 사용).
- **C_PlayerInputSource** → **플레이어 캐릭터** 엔티티 (그 엔티티의 Guid를 Session의 `m_playerGuid`에 넣음).
- **C_BossBrain** → **보스/적 캐릭터** 엔티티 (그 엔티티의 Guid를 Session의 `m_bossGuid`에 넣음).

나머지(`C_CombatContracts`, `C_Fighter`, `C_ActionFsm`, `C_CombatEventBus`, `C_CombatResolver`)는 컴포넌트가 아니라 코드/데이터 클래스라 **어떤 오브젝트에도 붙이지 않고**, `C_CombatSession`이 내부에서만 사용합니다.
